
## Что это такое
Сервис rate limiter это механизм контроля, который ограничивает количество запросов, которые пользователь или система могут отправить за определённый промежуток времени.

## Для чего

 - Предотвращение перегрузки системы. Ограничение количества запросов помогает избежать перегрузки серверов, что обеспечивает стабильную работу сервиса для всех пользователей. Лимиты позволяют гарантировать, что ни один пользователь не сможет монополизировать ресурсы системы

 - Управление затратами. Для сервисов, где оплата зависит от объёма запросов или использования ресурсов, rate limiting помогает контролировать расходы и прогнозировать затраты.

 - Контроль ресурсоёмких операций. Ограничение запросов к эндпоинтам, которые запускают ресурсоёмкие задачи, помогает избежать перегрузки системы.

## Примеры применения

- Публичные API: контроль количества запросов для обеспечения справедливого использования и защиты бэкенд-сервисов.
- Системы авторизации: ограничение попыток входа для предотвращения брутфорс-атак.
- Интеграция с другими сервисами: если приложение выступает в роли шлюза или прокси, rate limiting запросов к нижестоящим сервисам помогает соблюдать их квоты использования.
- Экспорт/импорт данных: ограничение частоты операций с большими объёмами данных.

## Как это работает

В этом сервисе реализован алгоритм **token bucket**. Для каждого клиента создается "ведро" с токенами:
- Ведро имеет максимальный размер `burst` (сколько запросов можно пропустить одномоментно);
- Ведро пополняется токенами со скоростью `rate` (сколько запросов в среднем разрешено за единицу времени);
- Каждый входящий запрос пытается забрать один токен.

Если токены в ведре есть — запрос разрешается. Если токенов нет, запрос отклоняется как превышающий лимит. Такой подход одновременно разрешает короткие всплески нагрузки и удерживает стабильный средний RPS на длинном интервале.

Типичный сценарий для web-сайта: защита каталога товаров, цен и карточек от массового парсинга ботами или защита URL аутентификации.
При каждом обращении к чувствительным endpoint'ам (например, `/catalog`, `/product/{id}`, `/search`, `/auth` и пр.) приложение отправляет в сервис rate limiter запрос в формате `group_name:client_id`.

Где `group_name` - идентификатор группы защищаемых ресурсов, напр. `api` - в нее попадают, к примеру, endpoint'ы `/auth`, `/restore_password` и т.п.

В качестве `client_id` обычно используют то, что каким-то образом идетифицирует конкретного клиента:
- `user_id` для авторизованных пользователей;
- `session_id` или хеш `IP+User-Agent` для гостей и т.п.

Сервис позволяет настроить несколько групп ограничений, например для запросов к API, к web-приложению, сервису аутентификации и т.д. Для каждой группы ограничений можно указать скорость пополнения токенов и размер bucket.

Например, для группы `web` задают умеренный `rate` и небольшой `burst`, чтобы обычный пользователь мог переходить по страницам сайта, а автоматический сборщик быстро упирался в лимит. А для группы `auth` значения `rate` и `burst` минимальны для более жесткого ограничения.
А если приложение распознало бота или парсер, то проверку можно перенаправить в группу с максимальными ограничениями.

Если сервис отвечает `0`, то лимит запросов не превышен.
При ответе `1` (лимит превышен), то например, веб-приложение:
- временно блокирует выдачу данных (HTTP `429 Too Many Requests`);
- показывает капчу или страницу "слишком много запросов";
- может повышать время блокировки при повторных превышениях.

Сценарии применения этого сервиса не ограничены только web, т.к. он представляет собой TCP сервер и может применяться в инфраструктурных службах.

## Что внутри

- TCP сервер (порт по умолчанию `49105`) - сервис rate limiter
- HTTP сервер (порт по умолчанию `8090`) - управляющий сервер

## Запуск сервиса

### DEV окружение
1. Создайте локальный конфиг:

```bash
cp dist.config.toml config.toml
```

2. Запустите сервис:

```bash
go run ./cmd/main.go --config ./config.toml
```

Или через `make`:

```bash
make run-default
```

Или в docker контейнере:

```bash
make run-in-docker
```

### Production окружение
```bash
./ratelimiter --config ./config.toml
```

## Cервис RateLimiter


### Формат запроса и ответа ratelimiter

Формат входящего сообщения:

```text
group_name:client_id
```

Пример:

```text
api:f3624d34efa74ce6bb676a607ae6f1e2
```

Правила:
- разделитель строго `:`
- должно быть 2 части: `group_name` и `client_id`
- пустые значения недопустимы
- длина входящего пакета ограничена `packet_size`

Где,
 - **group_name** это имя группы ограничений, напр. api или web и т.д.
 - **client_id** - это идентификатор клиента (это id пользователя или приложения, чьи запросы мы хотим ограничить)

Ответы сервиса:

| Ответ | Описание |
| --- | --- |
| `0` | запрос разрешен |
| `1` | лимит превышен |
| `e:invalid_data` | неверный формат запроса |
| `e:group_not_found` | группа не найдена |
| `e:read_timeout` | сервер не считал запрос, медленный клиент |
| `e:busy` | превышен лимит одновременных соединений к сервису|
| `e:internal` | внутренняя ошибка сервера |

> NB: ответ с префиксом `e:` означает, что произошла ошибка

## Настройки

Настройки можно задавать в файле конфигурации в формате TOML (опция `--config`) и переопределять их значения  через переменные окружения с префиксом `RATE_LIMITER_`. Переменные окружения имеют больший приоритет.

Пример: параметр `port` из файла конфигурации переопределяется переменной окружения с именем `RATE_LIMITER_PORT=5000`, `http_secret` как `RATE_LIMITER_HTTP_SECRET=mysecret` и т.д.

Основные параметры:

| Параметр | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `port` | `uint` | `49105` | порт TCP сервера |
| `http_port` | `uint` | `8090` | порт HTTP control API |
| `max_connections` | `int` | `1000` | максимальное число одновременных TCP соединений к сервису |
| `worker_pool_size` | `int` | `100` | размер пула воркеров |
| `read_timeout` | `duration` | `100ms` | таймаут чтения TCP запроса |
| `write_timeout` | `duration` | `100ms` | таймаут записи TCP ответа |
| `shutdown_timeout` | `duration` | `5s` | таймаут graceful shutdown |
| `packet_size` | `int` | `512` | максимум байт во входящем TCP сообщении |
| `cleanup_interval` | `duration` | `12h` | частота очистки неактивных лимитов |
| `ttl` | `duration` | `48h` | TTL лимита пользователя |
| `http_secret` | `string` | `secret` | значение заголовка `X-Auth-Token` для control API |
| `basic_auth_user` | `string` | `user` | логин basic auth для `/debug/pprof/*` |
| `basic_auth_pass` | `string` | `password` | пароль basic auth для `/debug/pprof/*` |
| `groups` | список | - | список групп лимитов (обязателен) |

> NB: Valid time units in duration are "ns", "us" (or "µs"), "ms", "s", "m", "h".

Параметры группы:

| Параметр | Тип | Ограничения | Описание |
| --- | --- | --- | --- |
| `name` | `string` | обязательно | имя группы |
| `rate` | `float` | обязательно, `> 0` | скорость пополнения токенов |
| `burst` | `int` | обязательно, `> 0` | размер bucket |



Пример `config.toml`:

```toml
port = 49105
http_port = 8090
max_connections = 10000
worker_pool_size = 100
read_timeout = "100ms"
write_timeout = "100ms"
shutdown_timeout = "5s"
packet_size = 512
cleanup_interval = "12h"
ttl = "48h"
http_secret = "secret"
basic_auth_user = "user"
basic_auth_pass = "password"

[[groups]]
name = "default"
rate = 20.0
burst = 100
```

## Управляющий сервер

Управляющий сервер работает на `http_port` и используется для получения статистики, управления группами лимитов и профилирования.

### Авторизация и заголовки

- Для endpoint'ов управления (`/stat`, `/info`, `/group_*`, `/enable_prof`, `/disable_prof`) обязателен заголовок `X-Auth-Token: <http_secret>` (настройка `http_secret`).
- При неверном или отсутствующем `X-Auth-Token` сервер возвращает `401 Unauthorized`.
- Для endpoint'ов профилирования `/debug/pprof/*` используется Basic Auth (`basic_auth_user` / `basic_auth_pass`).
- Для endpoint `/health` авторизация не требуется.
- Во все ответы endpoint'ов (кроме /health) добавляется заголовок `X-Track-Id`, его значение уникальное для каждого запроса.

### Единый формат JSON-ответа control API

Для всех endpoint'ов управления (кроме `/health` и `/debug/pprof/*`) используется единый JSON-формат:

```json
{
  "error": false,
  "data": {}
}
```

- `error: false` для успешного ответа.
- `error: true` для ошибки.
- `data` содержит полезные данные или текст ошибки.

### Endpoint'ы

#### `GET /health`

- Назначение: проверка доступности HTTP-сервера.
- Авторизация: не требуется.
- Успешный ответ:
  - `200 OK`
  - `Content-Type: text/plain; charset=utf-8`
  - Body: `ok`

#### `GET /stat`

- Назначение: получить количество активных limiter-объектов по группам.
- Авторизация: `X-Auth-Token`.
- Успешный ответ:
  - `200 OK`
  - JSON:

```json
{
  "error": false,
  "data": {
    "default": 42,
    "web": 13
  }
}
```

- Структура `data`: `map[string]int` (`group_name -> count`).

#### `GET /info`

- Назначение: получить расширенную информацию по группам.
- Авторизация: `X-Auth-Token`.
- Успешный ответ:
  - `200 OK`
  - JSON:

```json
{
  "error": false,
  "data": [
    {
      "name": "default",
      "count": 42,
      "rate": 20,
      "burst": 100
    }
  ]
}
```

- Структура элемента массива `data`:
  - `name: string`
  - `count: int`
  - `rate: float`
  - `burst: int`

#### `POST /group_add`

- Назначение: добавить новую группу ограничений.
- Авторизация: `X-Auth-Token`.
- Тело запроса:

```json
{
  "name": "new_group",
  "rate": 5.5,
  "burst": 7
}
```

- Поля запроса:
  - `name: string`
  - `rate: float`
  - `burst: int`
- Успешный ответ:
  - `200 OK`
  - JSON:

```json
{
  "error": false,
  "data": true
}
```

#### `POST /group_update`

- Назначение: обновить параметры существующей группы.
- Авторизация: `X-Auth-Token`.
- Тело запроса:

```json
{
  "name": "new_group",
  "rate": 10,
  "burst": 20
}
```

- Поля запроса:
  - `name: string`
  - `rate: float`
  - `burst: int`
- Успешный ответ:
  - `200 OK`
  - JSON:

```json
{
  "error": false,
  "data": true
}
```

#### `POST /group_delete`

- Назначение: удалить группу по имени.
- Авторизация: `X-Auth-Token`.
- Тело запроса:

```json
{
  "name": "new_group"
}
```

- Поля запроса:
  - `name: string`
- Успешный ответ:
  - `200 OK`
  - JSON:

```json
{
  "error": false,
  "data": true
}
```

Примечание: удаление несуществующей группы не считается ошибкой и тоже возвращает успешный ответ.

#### `POST /enable_prof`

- Назначение: включить runtime-профилирование (`block` и `mutex`).
- Авторизация: `X-Auth-Token`.
- Тело запроса: отсутствует.
- Успешный ответ:
  - `200 OK`
  - JSON:

```json
{
  "error": false,
  "data": true
}
```

#### `POST /disable_prof`

- Назначение: выключить runtime-профилирование.
- Авторизация: `X-Auth-Token`.
- Тело запроса: отсутствует.
- Успешный ответ:
  - `200 OK`
  - JSON:

```json
{
  "error": false,
  "data": true
}
```

#### `GET /debug/pprof/`
#### `GET /debug/pprof/cmdline`
#### `GET /debug/pprof/profile`
#### `GET /debug/pprof/symbol`
#### `GET /debug/pprof/trace`

- Назначение: стандартные endpoint'ы `net/http/pprof`.
- Авторизация: только Basic Auth.
- Формат ответов: стандартный для `pprof` (не оборачивается в `{"error","data"}`).

### Возможные HTTP коды ошибок

| HTTP код | Когда возникает |
| --- | --- |
| `400 Bad Request` | Некорректный JSON в теле запроса (`incorrect data`); невалидные параметры при создании группы (`ErrInvalidData`). |
| `401 Unauthorized` | Неверный или отсутствующий `X-Auth-Token` для control endpoint'ов. |
| `404 Not Found` | Попытка обновить несуществующую группу (`group not found`). |
| `409 Conflict` | Попытка добавить уже существующую группу (`group already exists`). |
| `500 Internal Server Error` | Необработанная внутренняя ошибка; ошибка кодирования JSON ответа. |
